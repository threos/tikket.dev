This page covers the most common faults when you self-host Tikket, and how to correct them.

## Onboarding and Setup

### Stripe payment features do not work

Paid events and the Stripe app in the app store are not available, or payment features show errors.

The Stripe integration needs several environment variables. They live in two files: `.env` in the root of the repository, and `.env.appStore`. If a variable is missing or empty, Tikket marks the Stripe app as not installed and turns off the payment features.

To correct the fault, add these variables to the `.env` file:

```env
STRIPE_PRIVATE_KEY=sk_test_...
STRIPE_CLIENT_ID=ca_...
STRIPE_WEBHOOK_SECRET=whsec_...
```

Add this variable to the `.env.appStore` file, or to `.env` if you use one file:

```env
NEXT_PUBLIC_STRIPE_PUBLIC_KEY=pk_test_...
```

Replace the values with your Stripe API keys from the [Stripe Dashboard](https://dashboard.stripe.com/apikeys). If you do not need payment features, leave the variables empty. Tikket then runs without the Stripe features.

## URL and Redirects

### Redirect to `localhost:3000` after deployment

After you deploy Tikket to a server or a domain, login redirects and internal links point to `http://localhost:3000` instead of your domain.

The environment variables `NEXTAUTH_URL` and `NEXT_PUBLIC_WEBAPP_URL` are not set to your production domain. These variables tell Tikket and NextAuth where the app runs.

To correct the fault, set your domain in the `.env` file:

```env
# Replace with your actual domain
NEXT_PUBLIC_WEBAPP_URL=https://cal.yourdomain.com
NEXTAUTH_URL=https://cal.yourdomain.com
```

Do not add a trailing slash. `NEXTAUTH_URL` is optional when `NEXT_PUBLIC_WEBAPP_URL` is set. Without `NEXTAUTH_URL`, NextAuth reads the base URL from the `Host` header of the incoming request. For Vercel deployments, you do not have to set `NEXTAUTH_URL`. Vercel reads it from the `VERCEL_URL` environment variable.

For Docker deployments, set these variables before you build the image. `NEXT_PUBLIC_WEBAPP_URL` is a build-time variable, and Next.js writes its value into the build. After you change it, build the image again.

## Docker

### API v2 service does not start

After `docker compose up -d`, the `calcom-api` service does not start, or it exits at once. The web app works, but the API v2 endpoints under `/api/v2/` return connection errors.

The API v2 service needs several environment variables that are not in the root `.env.example`. If one of them is missing, the service stops at startup with a `Missing environment variable` error.

To correct the fault, add these variables to the root `.env` file. The `docker-compose.yml` file passes them to the `calcom-api` service:

```env
# Required for API v2 (service will not start without these)
REDIS_URL=redis://redis:6379
JWT_SECRET=your_random_jwt_secret_here
NEXTAUTH_SECRET=your_nextauth_secret_here
CALENDSO_ENCRYPTION_KEY=your_32_character_encryption_key
STRIPE_API_KEY=sk_test_your_stripe_key
STRIPE_WEBHOOK_SECRET=whsec_your_webhook_secret

# Optional (have sensible defaults)
WEB_APP_URL=https://cal.yourdomain.com
REDIS_PORT=6379
LOG_LEVEL=warn
```

`STRIPE_API_KEY` is the API v2 equivalent of `STRIPE_PRIVATE_KEY` in the web app. Both are Stripe secret keys, but different services read them. If you do not need Stripe in the API, set a placeholder value such as `sk_test_placeholder`. The variable must be present.

Generate the secrets with:

```bash
openssl rand -base64 32
```

Then restart the stack:

```bash
docker compose down && docker compose up -d
```

If the service still fails, read its logs:

```bash
docker compose logs calcom-api
```

The API v2 service has its own example file at `apps/api/v2/.env.example`. It lists every supported variable.

### `CLIENT_FETCH_ERROR` in the logs

This error appears in the Docker logs, and login or the session fails:

```
[next-auth][error][CLIENT_FETCH_ERROR]
request to http://<your-domain>/api/auth/session failed, reason: getaddrinfo ENOTFOUND
```

The Docker container cannot resolve the external hostname in `NEXTAUTH_URL` from inside its network.

To correct the fault, add your domain to the `/etc/hosts` file of the container, so that the domain resolves to the container itself:

```yaml
# docker-compose.yml
services:
  calcom:
    extra_hosts:
      - "cal.yourdomain.com:127.0.0.1"
```

The container can then resolve your public domain internally, and `NEXTAUTH_URL` keeps your public URL. OAuth callbacks need the public URL.

This solution works when `NEXTAUTH_URL` uses HTTP, for example `http://cal.yourdomain.com:3000`. If `NEXTAUTH_URL` uses HTTPS, the container connects to `127.0.0.1:443`, but the app listens on port 3000, and the connection fails. In that case, run your reverse proxy inside the Docker network, or read the SSL section below.

Do not set `NEXTAUTH_URL` to `localhost`. It removes the DNS error, but it breaks OAuth. External providers such as Google then redirect to `localhost` instead of your domain.

### SSL and HTTPS behind a reverse proxy

Requests fail with SSL certificate errors when Tikket runs behind a load balancer or a reverse proxy that terminates HTTPS. Choose one of the three solutions below.

#### Solution 1: the proxy forwards HTTP internally

This is the most common setup. Keep `NEXTAUTH_URL` set to your public HTTPS URL:

```env
NEXTAUTH_URL=https://cal.yourdomain.com
```

Then configure the reverse proxy to forward these headers, so that internal requests work:

```nginx
# Nginx example
proxy_set_header Host $host;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header X-Forwarded-Host $host;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

Do not set `NEXTAUTH_URL=http://localhost:3000`. It removes the internal SSL errors, but it breaks OAuth callbacks. External providers such as Google and Microsoft then redirect users to `localhost`, and the redirect fails. Always use your public URL.

#### Solution 2: self-signed certificates internally

If your proxy uses a self-signed certificate, add your internal CA to the trusted certificates of Node. A CA is a certificate authority that signs certificates. Set the path to the CA file in this variable:

```env
NODE_EXTRA_CA_CERTS=/path/to/your-internal-ca.crt
```

#### Solution 3: turn off certificate verification (last resort)

Do not use this solution in production. It turns off TLS certificate verification for every connection, including calls to Stripe, Google Calendar and other external services. An attacker between your server and those services can then read and change the traffic. Use it only in an isolated development environment where you control all network traffic.

```env
NODE_TLS_REJECT_UNAUTHORIZED=0
```

## Database

### First user setup fails

The `/setup` page shows an error when you try to create the first admin user.

This happens if the database migrations are not applied, or if the database is in an inconsistent state.

To correct the fault:

1. Apply the database migrations:

   ```bash
   # For development
   yarn workspace @calcom/prisma db-migrate

   # For production / Docker
   yarn workspace @calcom/prisma db-deploy
   ```

2. Make sure that the database is reachable and that `DATABASE_URL` in `.env` is correct.

3. If the error remains after the migrations, read the application logs for the Prisma error message. It names the field or constraint that fails.

The setup endpoint (`/auth/setup`) creates the first user with the `ADMIN` role. It only works when the `User` table is empty. If an earlier setup attempt partly succeeded, clear the users table by hand before you try again.
